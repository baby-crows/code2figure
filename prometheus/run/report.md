## 3. The design claim the figure carries (T2 rule 6)

Found in the repo's own words, `README.md#L29-L30`:

```
* No dependency on distributed storage; single server nodes are autonomous
* An HTTP pull model for time series collection
```

Corroborated by `docs/storage.md#L10-L29` (local on-disk TSDB, WAL replayed on restart) and `docs/storage.md#L59-L63` ("not clustered or replicated ... should be managed like any other single node database").

This claim is about **what does not cross a boundary** and **who starts a connection**, so per the skill's device table it is carried by the *structure*, not by a banner:

- one solid green zone holds every stateful component; the two dashed zones hold everything else;
- **every** data-plane arrow that crosses the green border starts inside it — `discovery.Manager → SD sources`, `scrapeLoop → Targets`, `notifier → Alertmanager`, `Fanout → remote write`. The returned data comes back on a separate dashed arrow. The only call that starts outside is the human's `GET /api/v1/query`;
- the store is the largest and the only blue-filled box, and the whole `wal/ → Head → blocks` chain sits inside the green zone, so "no external state" is checkable against the drawing rather than believed;
- the loop-back arrow `rules.Manager → TSDB` shows that rule results re-enter the same database.

## 7. Assumptions and things not drawn

- Server mode only. Agent mode (`--agent`, `docs/prometheus_agent.md`) skips the rule manager and the query engine; it is not in the figure.
- Out-of-order ingestion (`wbl/`), exemplars, metadata records, native histograms, federation, OTLP ingest, tracing and the `remote read` path exist in the code but are omitted to keep eight stages readable.
- "one HTTP path each" for targets is the shape of the pull model, not a claim that a target can expose only one endpoint.
- The `2h → 6h → 18h` blocks are the first three of `ExponentialBlockRanges(2h, 10, 3)`; the series continues, which is what the merging arrows imply rather than the drawing enumerating them.

## Open question for you (T2-5)

The stage boundaries are the thing most likely to be wrong. Specifically:

1. Is `storage.Fanout` (4) worth its own stage, or should it collapse into the TSDB box?
2. Should `promql.Engine` (7) sit before `rules.Manager` (6)? I numbered rules first because the rule manager is the caller and the engine is what it calls, but a reader may expect the query path to come first.
3. Who is the reader? A new contributor wants process boundaries (what this draft optimises for); an operator would want the config keys and the on-disk paths made larger instead.
